# 一、并发与状态流转

## 1.1 用无状态条件的 update 改订单状态 → 已取消的单被"付款复活"

**现象**

订单状态流转本来写的是：

```java
orderMapper.update(Orders.builder().id(id).status(2).build());   // where id = ?
```

**根因**

`OrderMapper.update` 的 SQL 只有 `where id = #{id}`，**没有状态条件**。于是：

```
t1  用户点支付      → update status = 2
t2  OrderTask 发现这单超过 15 分钟未支付 → update status = 6 已取消
结果 status 又被 t1 改回 2 —— 一张已取消的订单被付款复活了
```

**这不是假想场景**：`OrderTask` 每分钟扫一次（`@Scheduled(cron = "0 * * * * ?")`），在 15 分钟的分界线附近必然有窗口。

**解法：CAS（条件更新）+ 影响行数判断**

```sql
update orders set status = 2, pay_status = 1, checkout_time = now()
where id = #{id} and status = 1
```

```java
int rows = orderMapper.updatePaymentSuccess(id);
if (rows == 0) throw new OrderBusinessException(ORDER_STATUS_ERROR);
```

`1` = 我赢了；`0` = 状态已被别人改（重复支付 / 刚被取消）。

**一句话**：**凡是"基于当前状态做决策"的写操作，都要把状态条件写进 SQL。**

## 1.2 只靠"购物车非空"防重复提交 → 并发下产生两张订单

**现象**

用户连点两次"提交订单"，两张订单。

**根因**

第一次尝试的写法是"下单前校验购物车非空"：

```
两个并发请求
  → 都读到购物车非空（都是快照读）
  → 都通过校验
  → 各自插入一张订单
```

**解法：用"清空购物车"的 `DELETE` 影响行数做无锁抢占**

```java
int cleared = shoppingCartMapper.deleteByUserId(userId);   // 需要把返回值 void 改成 int
if (cleared == 0) {
    throw new ShoppingCartBusinessException(SHOPPING_CART_IS_NULL);   // 并发下我输了
}
```

为什么要放在 `insert orders` **之前**：输的那个请求只需回滚，不用白做一次插入。

为什么不需要 Redis 锁：`DELETE` 是写操作（当前读），两个并发事务里只有一个能影响那些行；另一个被行锁挡住，等对方提交后影响 0 行。**把"判断"合并进"本来就要做的写操作"，零额外成本。**

配合 `@Transactional`，抢占后如果后续失败会整体回滚，购物车不会丢。

**一句话**：**能合并进数据库写操作的并发判断，就不要再引入分布式锁。**

**验证方式**：用 HttpClient 同时发两个请求（不是先后发），断言"只生成 1 张订单 + 输的那个 code=0"。

## 1.3 `@Transactional` 对**受检异常**不回滚

**现象**

抢占成功后如果后续抛异常，购物车的删除没有回滚 → 用户加的东西凭空消失。

**根因**

Spring 的 `@Transactional` **默认只对 `RuntimeException` 和 `Error` 回滚**，对受检异常（`extends Exception`）**不回滚**。

本项目能正常回滚，是因为 `BaseException extends RuntimeException`：

```java
public class BaseException extends RuntimeException { ... }
```

如果哪天有人把业务异常改成受检异常，**所有依赖回滚的逻辑会静默失效**。

**解法**

- 业务异常一律继承 `RuntimeException`
- 或者显式声明 `@Transactional(rollbackFor = Exception.class)`

**一句话**：**"事务没回滚"最常见的原因就是异常类型不对，而不是事务没生效。**

---

## 1.4 WebSocket 推送放进事务里 → 事务回滚了消息却发出去了

**现象**

支付成功后推"来单提醒"给商家。如果推送写在事务方法里，事务后续失败回滚时，**消息已经发出去了**，商家收到一条对应不存在订单的提醒。

**根因**

推送是**外部副作用、不可回滚**。数据库能回滚，HTTP/WebSocket 调用不能。

**解法**

- 支付方法**不加** `@Transactional`（它只有一条 UPDATE，单条 SQL 本身就是原子的）
- 顺序：**CAS 成功 → 再推送**
- 如果必须在事务里，用 `TransactionSynchronizationManager.registerSynchronization(...)` 在 `afterCommit` 里推

**一句话**：**事务里只放可回滚的操作；通知、短信、外部调用放到事务提交之后。**

# 二、MyBatis 与数据库

## 2.1 动态 `<set>` 只去**尾部**逗号

**现象**

```xml
<set>
    <if test="status != null">status = #{status},</if>
    <if test="riderId != null">rider_id = #{riderId},</if>
    <if test="riderPhone != null">rider_phone = #{riderPhone}</if>
</set>
```

报 `SQLSyntaxErrorException`，位置看起来莫名其妙。

**根因**

`<set>` 标签**只会删掉最后一个多余的逗号**。如果中间某一行因为 `<if>` 不成立被跳过，或者手写时漏了逗号，拼出来的 SQL 就是：

```sql
set status = 1 rider_id = 2, ...
--              ↑ 这里少一个逗号
```

**解法（本项目的选择）**

订单模块的 5 个状态流转 SQL **全部写成静态 SQL**，不动态拼字段：

```xml
<update id="updateConfirmOrder">
    update orders set status = #{status} where id = #{id} and status = 2
</update>
```

一眼就能看对，也不会有逗号问题。

**一句话**：**能写静态 SQL 就别动态拼；动态 SQL 的逗号问题在编译期和运行前都发现不了。**

---

## 2.2 显式传 NULL 时，数据库的 `DEFAULT` **不生效**

**现象**

`orders` 表的 `delivery_status` 是 `NOT NULL DEFAULT 1`，代码没给它赋值，插入报：

```
java.sql.SQLIntegrityConstraintViolationException: Column 'delivery_status' cannot be null
```

**根因**

**`DEFAULT` 只在「INSERT 语句里根本不包含这一列」时才生效。**

MyBatis 的 insert 是**显式列出所有列**的：

```sql
insert into orders (number, status, ..., delivery_status, ...) values (?, ?, ..., ?, ...)
```

传了 NULL 就是 NULL，**直接撞 NOT NULL 约束，DEFAULT 用不上**。

**解法**

在 Java 侧兜底默认值（业务含义清晰）：

```java
orders.setDeliveryStatus(dto.getDeliveryStatus() == null ? 1 : dto.getDeliveryStatus());
orders.setTablewareStatus(dto.getTablewareStatus() == null ? 1 : dto.getTablewareStatus());
```

**为什么这个坑值得记**

- 数据库给了 DEFAULT 会让人误以为"不传就行"
- 报错信息只说 `cannot be null`，**不会提示"其实你有 DEFAULT"**，容易怀疑到别的地方
- 排查时要核对 `information_schema` 的 NOT NULL 列，而不是只看 Java 代码

**一句话**：**`DEFAULT` 是"列被省略"时的兜底，不是"值为 NULL"时的兜底。**

**排查 SQL**

```sql
SELECT COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT
FROM information_schema.columns
WHERE table_schema = 'sky_take_out' AND table_name = 'orders' AND IS_NULLABLE = 'NO'
ORDER BY ORDINAL_POSITION;
```

## 2.3 `@Insert` 注解不配 `useGeneratedKeys` → 主键不回填

**现象**

测试里插入一条地址，然后 `addressBook.getId()` 是 `null`，最终在 `Map.of(...)` 上 NPE。

**根因**

```java
@Insert("insert into address_book (...) values (...)")
void insert(AddressBook addressBook);      // ← 没配 useGeneratedKeys
```

对比 `OrderMapper.insert`（XML 里配了）：

```xml
<insert id="insert" useGeneratedKeys="true" keyProperty="id">
```

**只有配了的才会把自增主键回填到对象上。**

**解法**

- 生产代码需要主键 → 补 `useGeneratedKeys = true, keyProperty = "id"`
- **测试里**不想改生产代码 → 插完再查一次把 id 取出来

**一句话**：**"插入成功但 getId() 是 null"，先看 Mapper 有没有配 `useGeneratedKeys`。**

## 2.5 没索引的查询：全表扫描 + filesort

**现象**

C 端"我的订单"：

```sql
select * from orders where user_id = ? order by order_time desc
```

`EXPLAIN` 结果：

```
type = ALL            ← 全表扫描
possible_keys = NULL  ← 压根没有可用索引
Extra = Using where; Using filesort
```

**根因**

`orders` 表**只有主键索引和订单号唯一索引**，`user_id` 上没有索引。`order_detail.order_id` 同样没有。

**解法**

```sql
CREATE INDEX idx_order_detail_order_id ON order_detail (order_id);
CREATE INDEX idx_orders_user_time      ON orders (user_id, order_time);
CREATE INDEX idx_orders_status_time    ON orders (status, order_time);
```

`(user_id, order_time)` 这个顺序的两个作用：

- `user_id` 在最左 → 过滤走索引，不再全表扫描
- 索引里包含 `order_time` → **排序直接用索引顺序，省掉 filesort**（最左前缀 + 利用索引排序）

完整脚本见 `docs/sql/02-order-indexes.sql`。

**⚠️ 一个反直觉的验证问题**

表里只有 3 行数据时，**加了索引 `EXPLAIN` 仍然会显示 `type=ALL`**——优化器认为小表全扫更快。

所以想立刻验证索引可用，要用 `FORCE INDEX`：

```sql
EXPLAIN SELECT * FROM orders FORCE INDEX (idx_orders_user_time)
WHERE user_id = 5 ORDER BY order_time DESC;
```

`filesort` 消失，就是"索引带上了排序"的证据。

**一句话**：**索引的正确性由"查询形态"决定，不由数据量决定——但"是否被使用"依赖数据量。**

另：判断索引该不该加的标准是 —— **每个索引都要能说出它服务哪个查询**。说不出来的就是多余的（比如单独的 `orders(status)`：区分度只有 6 个值，优化器大概率不用）。

# 三、Java 语言细节

## 3.1 `Long != Long` 比较的是**引用**，不是值

**现象**

归属校验写成：

```java
if (user.getId() != orders.getId()) { throw new OrderBusinessException(ORDER_NOT_FOUND); }
```

测试数据下"看起来正常"，上线后行为诡异。

**根因**

`Long` 是包装类型，`!=` 比的是**对象引用**。`Long` 缓存只覆盖 **-128 ~ 127**：

- id 在这个范围内 → 同一个缓存对象 → `!=` 能"正确"工作
- id 超过 127 → 两个不同的对象 → **即使值相等，`!=` 也返回 true**

**所以这个 bug 在测试数据（id 都很小）里根本发现不了。**

**解法**

```java
if (!java.util.Objects.equals(orders.getUserId(), userId)) { ... }
```

用 `Objects.equals` 的额外好处：**`userId` 为 null 时不会 NPE**（在非 HTTP 线程如定时任务里，`BaseContext` 取出来就是 null）。

**一句话**：**包装类型比较永远用 `equals` / `Objects.equals`，永远不用 `==` / `!=`。**

---

## 3.2 `Map.of(...)` 不接受 null 值

**现象**

```java
Map.of("addressBookId", othersAddress, "payMethod", 1)   // othersAddress 为 null
```

直接 `NullPointerException`，堆栈指向这一行，看不出是哪个值为 null。

**根因**

`Map.of` 是**不可变 Map 的工厂方法，明确禁止 null 键和 null 值**。`HashMap` 允许，`Map.of` 不允许。

**解法**

- 先确认值不为 null
- 或者用 `new HashMap<>()` 逐个 `put`

**一句话**：**`Map.of` 的 NPE 往往不是 Map 的问题，而是你的某个值本来就是 null** —— 顺着栈找"哪个值没取到"。

## 3.3 `BeanUtils.copyProperties`：`Integer → int` 且值为 null 会抛异常

**现象**

```java
BeanUtils.copyProperties(ordersSubmitDTO, orders);
```

报：

```
org.springframework.beans.FatalBeanException: Could not copy property 'packAmount' from source to target;
nested exception is java.lang.IllegalArgumentException:
java.lang.NullPointerException: Cannot invoke "java.lang.Number.intValue()" ...
```

**根因**

`Orders.packAmount` / `tablewareNumber` 当时是**原始类型 `int`**，而 `OrdersSubmitDTO` 里对应字段是 `Integer`。

前端不传 → DTO 里是 `null` → Spring 反射把 null 往 `int` 里写 → 炸。

**注意**：实体是 `Integer` 时就没这个问题（本项目后来把实体字段改成 `Integer` 了）。

**解法（三个层次）**

1. **改实体字段为包装类型** `Integer` —— 最省事
2. **不用整对象拷贝，改成手工 `set`** —— 最明确，也顺带解决"哪些字段其实不该来自前端"
3. 拷贝前给 DTO 的 null 字段兜默认值

**本项目最后选的是 2**：下单接口每个字段从哪来本来就该写清楚。

**一句话**：**整对象 `copyProperties` 的代价是"隐式的字段来源"** —— 你不再知道每个字段是谁给的。

**验证方法（值得学的）**

写一个**独立的小探针程序**，用项目的依赖跑一遍，直接观察行为，而不是凭记忆猜：

```
java -cp "<spring-beans.jar>;<spring-core.jar>;<sky-pojo/target/classes>" Probe.java
```

## 3.4 常量用反：`UN_PAID` vs `PENDING_PAYMENT`

**现象**

支付接口写：

```java
if (!UN_PAID.equals(orders.getStatus()) || !PENDING_PAYMENT.equals(orders.getPayStatus())) {
    throw new OrderBusinessException(ORDER_STATUS_ERROR);
}
```

结果**任何订单都付不了款**。

**根因**

`Orders` 里两套状态常量**长得太像**：

```java
// 订单状态 status
public static final Integer PENDING_PAYMENT = 1;      // 待付款
// 支付状态 payStatus
public static final Integer UN_PAID = 0;              // 未支付
```

写代码时把"支付状态的常量"拿去比了 `status`：

| 写法 | 实际含义 |
|---|---|
| `UN_PAID.equals(orders.getStatus())` | 拿 0 比订单状态（=1）→ false |
| `PENDING_PAYMENT.equals(orders.getPayStatus())` | 拿 1 比支付状态（=0）→ false |

两个 `!` 都成立 → 永远抛异常。

**为什么特别容易犯**

- 中文语义上 `UN_PAID`（未支付）和 `PENDING_PAYMENT`（待付款）**几乎是同义词**
- 都是 `Integer`，**编译器抓不到类型不匹配**
- 都在同一个类里，**没有任何命名空间区分**
- IDE 自动补全时两个挨在一起

**解法**

```java
if (!PENDING_PAYMENT.equals(orders.getStatus()) || !UN_PAID.equals(orders.getPayStatus())) {
```

**根治建议**：把两套常量**分开**

```java
OrderStatus.PENDING_PAYMENT
PayStatus.UN_PAID
```

这样 `OrderStatus.UN_PAID` 这种写法**根本不存在**，编译期就错了。

**一句话**：**用类型/命名空间隔离"容易混淆的常量"，比写注释提醒自己有效得多。**

## 3.5 `&&` 与 `||` 的双重错误互相抵消 → 代码"看起来能跑"

> 这是本项目**最值得记的一条**，因为它会误导你去做错误的"修复"。

**现象**

```java
if (page == null && page.size() <= 0) {
    throw new OrderBusinessException(ORDER_NOT_FOUND);
}
```

**两个错误叠在一起：**

**错误一：`&&` 应该是 `||`**

`&&` 短路求值：

- `page == null` 为 true → 才会求值 `page.size()` → **NPE**
- `page != null`（实际情况）→ 左边 false → **整个条件恒为 false**

所以这个 `if` **从来没生效过**。

**错误二：这个判断的意图本身就是错的**

"用户还没有订单"是**正常状态**，不是错误。抛 `ORDER_NOT_FOUND` 意味着**新用户第一次打开"我的订单"会看到错误提示**。

**结果：两个错误互相抵消了。**

实测 `status=4`（无匹配）返回 `code=1, total=0, records=[]` —— **行为是对的**，因为那个错误的 throw 从没执行过。

**⚠️ 危险之处**

**谁"顺手修好"其中一个（把 `&&` 改成 `||`，这看起来是最自然的修正），立刻就把另一个错误暴露成线上问题。**

**正确动作：把这个 `if` 整段删掉。**

`OrderMapper.pageQuery` 返回 `Page<OrderVO>`，MyBatis 查列表**永远不会返回 null**，连 null 判断都不需要。

**一句话**：**遇到"看起来能跑但逻辑读不通"的代码，不要只修一半 —— 先搞清楚它为什么"碰巧能跑"，再决定是补全还是删除。**

## 3.6 项目声明 Java 1.8，代码却用了 Java 9+ 的 API

**现象**

测试代码里写了 `Map.of(...)` 和 `List.of()`。**`mvn test` 编译并运行成功（6/6 通过）**，
但 **IDE 报错"Cannot resolve method 'of'"**。

看起来像"IDE 误报"——**但 IDE 是对的。**

**根因：项目声明的 Java 版本是 1.8**

```
pom.xml → <parent>spring-boot-starter-parent 2.7.3</parent>

spring-boot-starter-parent-2.7.3.pom 里：
    <java.version>1.8</java.version>
    <maven.compiler.source>${java.version}</maven.compiler.source>
    <maven.compiler.target>${java.version}</maven.compiler.target>
```

而 `Map.of` / `List.of` / `Set.of` 是 **Java 9** 才加的 API。

**为什么 Maven 能编过（关键知识点）**

> **`-source` / `-target` 只控制「语言语法」和「字节码版本」，不控制「类库」。**
>
> 只有 `--release N`（或 `-bootclasspath`）才会限制可用 API 的版本。

所以 Maven 用 `-source 1.8 -target 1.8` 编译时，**编译器仍然使用 JDK 21 的 `rt` 类库**，
`Map.of` 能解析到，编译通过；运行时也是 JDK 21，所以**真的能跑**。

而 IDE 严格按"语言级别 1.8"检查，直接标红。

**这是真实隐患，不是误报**

- 本机 JDK 21 → 一切正常
- 换成 JDK 8 编译 → `Map.of` 找不到，**编译失败**
- 如果 CI 用 JDK 8、本地用 JDK 21，就会出现"本地能跑、流水线挂"

**解法：不要用 Java 9+ 的 API**

```java
// ❌ Map.of 是 Java 9+，而且不接受 null 值
Map.of("orderNumber", number, "payMethod", 1)

// ✅ 具名工具方法（可变参数，成对的 key/value）
private static Map<String, Object> body(Object... keyValues) {
    Map<String, Object> map = new HashMap<>();
    for (int i = 0; i < keyValues.length; i += 2) {
        map.put((String) keyValues[i], keyValues[i + 1]);
    }
    return map;
}
```

`List.of()` → `Collections.emptyList()`。

**顺带一个坑**：`Map.of` **不接受 null 值**（`HashMap` 允许）。
传了 null 会抛 NPE，而堆栈只指向 `Map.of(...)` 那一行，**看不出是哪个值没取到**。
本项目就是靠这个 NPE 才发现"`AddressBookMapper.insert` 没回填主键"（见 2.3）。

**一句话**：**`-source 1.8` 能编过不代表你能用 Java 9 的 API —— IDE 标红时先怀疑代码，别先怀疑 IDE。**

**排查命令**

```bash
# 看项目实际声明的 Java 版本（本项目的属性写在父 POM 里，项目自己没声明）
mvn help:evaluate -Dexpression=java.version -q -DforceStdout

# 更直接：读父 POM
#   mvn_repo/org/springframework/boot/spring-boot-starter-parent/<version>/spring-boot-starter-parent-<version>.pom

# 全项目扫一遍有没有 Java 9+ 的 API
#   grep -rn "Map\.of(\|List\.of(\|Set\.of(" --include=*.java
```

## 4.1 查询接口漏设 userId → 动态条件不生效，静默返回全部

**现象**

C 端"我的订单"分页查询：

- Controller 直接按 query 参数绑定 `OrdersPageQueryDTO`
- Service 拿 DTO 后**原样**传给 Mapper
- Mapper XML：

```xml
<if test="userId != null"> and user_id = #{userId} </if>
```

**`OrdersPageQueryDTO` 里正好有 `userId` 字段**（本来是给管理端按用户筛选用的）。

**两个攻击面**

| 前端行为 | 结果 |
|---|---|
| 不传 `userId` | `<if>` 不生效 → **SQL 里没有用户过滤 → 查全表** |
| 传 `userId=1` | 条件生效 → **直接查别人的订单** |

**实测证据**（user 5 的 token，库里订单 4 属于 user 1）：

```
不传 userId      → total=3  订单=[6, 5, 4]   ← 别人的订单 4 出现了
传 userId=1      → total=1  订单=[4]         ← 直接看别人的
```

**为什么危险：它是"静默"的**

| 检查项 | 结果 |
|---|---|
| SQL 语法 | ✅ 合法 |
| 查询执行 | ✅ 成功 |
| 返回数据 | ✅ **有数据** |
| 异常 / 警告 | ❌ 没有 |
| 功能测试 | ✅ "能查到订单，正常" |

**所有"正常"的信号都在，唯一的问题"数据范围不对"不体现在任何返回值里。**

**根因（三个环节各自都对，合起来就漏了）**

1. **Controller**：GET 请求 + 普通对象参数 → Spring 把 query 参数绑到 DTO → **DTO 里有什么字段，前端就能传什么**
2. **DTO**：复用了管理端的 DTO，**顺带继承了 `userId` 这个"身份入口"**
3. **Mapper**：`<if>` 的语义是"传了就用，没传就跳过" → **条件可以不存在**

**解法（四层，从浅到深）**

| 层次 | 做法 | 评价 |
|---|---|---|
| ① 绕过 | Service 里**无条件覆盖** `setUserId(BaseContext.getCurrentId())` | 能用，但依赖"每个开发者都记得写" |
| ② 收口 | C 端单独定义查询 DTO，**不含 `userId`** | 前端**从类型上就传不进来** |
| ③ 改造 SQL | 把 userId 从动态 `<if>` 拿出来，做成**必传参数** | 让"漏掉"变成编译期问题 |
| ④ 架构 | MyBatis 拦截器统一注入数据权限条件 | 大型系统/SaaS 做法 |

**⚠️ ① 的关键细节**：必须是**无条件覆盖**，不能写成"为 null 才设置"：

| 写法 | 结果 |
|---|---|
| `if (dto.getUserId() == null) dto.setUserId(当前用户)` | ❌ 前端传了值，条件不成立，**前端赢** |
| `dto.setUserId(当前用户)` | ✅ 服务端的值永远覆盖 |

**一句话**：**身份只能来自 token，并且要无条件覆盖参数里的同名值。**

## 4.2 `Objects.equals` 少个 `!` → 归属校验反向

**现象**

```java
if (Objects.equals(userId, orders.getUserId())) {
    throw new OrderBusinessException(ORDER_NOT_FOUND);
}
```

**实测结果**：

```
支付【自己的】订单 → code=0 「订单不存在」   ❌
支付【别人的】订单 → code=1 成功            ❌ 越权
```

**根因**

`Objects.equals(a, b)` 返回 true 的含义是「**它们相等**」，也就是「**这就是当前用户的订单**」——**这是正常情况，不该抛异常**。

**归属校验的语义永远是「不相等才拒绝」**：

```java
if (!Objects.equals(userId, orders.getUserId())) { ... }
```

**一句话**：`Objects.equals` 你选对了（避免 NPE），`ORDER_NOT_FOUND` 也选对了（不暴露订单是否存在）——**就差一个 `!`**。

## 4.3 金额直接用前端传的 `amount` → 用户一分钱下单

**现象**

```java
BeanUtils.copyProperties(ordersSubmitDTO, orders);   // amount 也被拷进去了
```

`OrdersSubmitDTO` 里**有 `amount` 字段**，直接用它入库，用户改一下请求体就能 0.01 元下单。

**解法：服务端重算**

```java
BigDecimal goodsAmount = shoppingCartList.stream()
        .map(c -> c.getAmount().multiply(BigDecimal.valueOf(c.getNumber())))
        .reduce(BigDecimal.ZERO, BigDecimal::add);
```

**⚠️ 必须注意 `shopping_cart.amount` 是「单价」不是「小计」**

核对过源码：`shoppingCart.setAmount(dish.getPrice())`。所以小计必须乘数量。

**漏乘的后果**：买 3 份只收 1 份的钱——**而且测试单份商品时永远发现不了**。

**一句话**：**凡是参与金额计算的前端参数，要么后端重算，要么校验边界，绝不裸收。**

## 4.4 参与金额的参数不校验范围 → 负数倒扣钱

**现象**

打包费暂时无法后端重算（还没有店铺配置），于是直接接受前端传的 `packAmount`。攻击：

```
POST /user/order/submit
{ "packAmount": -99999 }

→ amount = 52.00 + (-99999) = -99947.00
→ 一张「已支付、金额 -99947 元」的订单进库
```

**解法：卡上下限**

```java
if (packAmount < 0 || packAmount > MAX_PACK_AMOUNT) {
    throw new OrderBusinessException(PACK_AMOUNT_ERROR);
}
```

- **下界 0** → 防负数倒扣（**这是安全红线**）
- **上限** → 防脏数据污染统计

**一句话**：**校验的意义不是"防用户多付"，而是"防脏数据污染金额"。**

---

## 4.5 金额与统计的连带影响

`Orders.amount` 的字段注释是**「实收金额」**，而营业额统计直接取 `select sum(amount) from orders`。

所以"重算金额时漏了打包费"不只是少收钱，还会让**营业额统计偏低**。

**一句话**：**改金额计算前，先查清楚这个字段被谁用了。**

# 五、Spring / Spring Boot

## 5.1 两个 `@Service` 实现同一接口 → `NoUniqueBeanDefinitionException`

**现象**

把一个被注释的 Service 实现类放开后，应用**启动失败**：

```
NoUniqueBeanDefinitionException: expected single matching bean but found 2
```

**根因**

`OrderService` 接口本来是"一个接口一个实现"。当管理端和 C 端各自有一个实现类时，两个 `@Service` 都实现 `OrderService`，而注入点是 `@Autowired OrderService` → 无法确定用哪个。

**注**：这个问题**编译期不报错**，只有启动才炸。

**解法：按端拆接口**

```
OrderService       ← OrderServiceimplBusiness implements       （管理端）
OrderServiceUser   ← OrderServiceImplUser implements           （C 端）
```

**顺带的好处**：`OrderService` 里原本混着两端的职责，拆完命名也清晰了。

**一句话**：**"一个接口多个实现"在 Spring 里是合法的，但 `@Autowired` 按类型注入时会歧义 —— 拆接口比加 `@Qualifier` 更有表达力。**

## 5.2 改名后残留 `.class` → 重复 Bean，必须 `mvn clean`

**现象**

把 `OrderServiceimpl2` 改名为 `OrderServiceimplBusiness` 后，`mvn package` 成功，但启动报**两个 Bean 名字都存在**。

**根因**

`target/classes` 里**残留了旧的 `OrderServiceimpl2.class`**，Spring 扫描时把新旧两个类都注册了。

**解法**

```bash
mvn clean package
```

**一句话**：**Java 里"重命名/删除类"之后，一定要 `clean`**，否则 `target` 里的旧 class 会继续参与组件扫描。

## 5.3 `removeCurrentId()` 定义了但从未被调用 → ThreadLocal 串号

**现象**

`BaseContext` 是 ThreadLocal 存的"当前登录人"。原代码里：

```java
public static void removeCurrentId() { threadLocal.remove(); }
```

**定义了，但全项目没有任何地方调用它。**

**根因**

Tomcat 用**线程池**，线程会被复用。不清理的话，上一个请求的身份会带给下一个请求——**用户 A 的操作可能以用户 B 的身份执行**。

**解法**

在拦截器的 `afterCompletion` 里清理：

```java
@Override
public void afterCompletion(...) {
    BaseContext.removeCurrentId();
    BaseContext.removeCurrentRole();
}
```

**顺带**：定时任务、测试等"不经过拦截器的线程"里，`BaseContext.getCurrentId()` 会是 `null`，Service 层不能无条件假设它非空。

**一句话**：**ThreadLocal 的 `set` 和 `remove` 必须成对出现，生命周期是"一个请求"。**

---

## 5.4 拦截器改成 `/**` 默认拒绝，差点误伤公开接口

**现象**

为了让"新增一个端不会忘记加权限"变成安全默认，把拦截器注册改成：

```java
.addPathPatterns("/**")
.excludePathPatterns("/login", "/notify/**", /* knife4j 相关 */ ...)
```

**差点漏掉一个**：`/user/shop/status`（店铺营业状态）在改造前就是**公开**的——顾客在登录前就要能看到"营业中/已打烊"。默认拒绝之后它会被要求登录，**破坏了原有业务**。

**解法**

把它加回白名单，并写清楚原因：

```java
// C 端店铺营业状态：顾客在登录前就要能看到"营业中/已打烊"，
// 改造前它就是公开接口，这里保持原样，不要顺手收紧
"/user/shop/status",
```

**顺带验证**：`/ws/**`（WebSocket 握手）不是 `HandlerMethod`，会被 `if (!(handler instanceof HandlerMethod)) return true;` 放行——**实测确认过能连上**。

**一句话**：**改成"默认拒绝"时，必须把原来所有公开接口列出来逐一确认** —— 否则会把"功能坏了"当成"安全了"。

## 5.5 401 和 403 混用 → 用户被莫名登出

**现象**

越权访问如果用 401 返回，前端的统一拦截器会**清掉 token 并跳登录页**。于是骑手点一下不该点的按钮，就被登出了。

**解法**

| 情况 | 状态码 | 前端行为 |
|---|---|---|
| token 无效 / 缺失 / 过期 | **401** | 清 token，跳登录页 |
| token 有效但角色不对 | **403** | 只提示"没有权限"，**不动 token** |

**一句话**：**401 是"你是谁不知道"，403 是"知道你是谁，但你不能干这个"** —— 混用会让用户被无意义地登出。

# 六、测试

## 6.1 `@SpringBootTest` 默认 MOCK 环境与 WebSocket 冲突

**现象**

新写的集成测试**6 个用例全部 ERROR**，看起来像测试代码写错了：

```
Failed to load ApplicationContext
Caused by: Error creating bean with name 'serverEndpointExporter' ...
nested exception is java.lang.IllegalStateException:
javax.websocket.server.ServerContainer not available
```

**根因**

`@SpringBootTest` 默认 `webEnvironment = MOCK`，用的是**模拟的 ServletContext**，**没有真实的 WebSocket 容器**。而项目注册了 `ServerEndpointExporter`，它初始化时需要 `ServerContainer`。

**这是环境问题，不是测试逻辑问题** —— 但错误信息很容易让人去怀疑自己的测试代码。

**解法**

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
```

起一个真实的嵌入式 Tomcat。

**关键点**：即使起了真实容器，**MockMvc 仍然是"进程内直接调 DispatcherServlet"、不经过网络**，所以请求还在测试线程上，`@Transactional` 的回滚**依然有效**。

（如果用 `RANDOM_PORT` + `TestRestTemplate` 发真实 HTTP，请求在另一个线程执行，测试的事务管不到，**造的数据会真的落库**。）

**一句话**：**测试启动失败先看是"环境/容器"问题还是"测试逻辑"问题** —— 整个上下文加载失败时，所有用例一起 ERROR，通常不是你的断言写错了。

---

## 6.2 直接调 Service 测不出越权

**现象**

想测"用户 A 看不到用户 B 的订单"，很自然地写成：

```java
OrdersPageQueryDTO dto = new OrdersPageQueryDTO();
dto.setUserId(5L);                    // ← 你自己填的
orderServiceUser.pageOrder(dto);
```

**这个测试永远是绿的**，因为它测不出那个 bug。

**根因**

真实的漏洞链条是：

```
HTTP ?userId=1  →  Spring 参数绑定  →  DTO.userId = 1  →  没人覆盖  →  查了别人
                        ↑
                  漏洞就在这一层
```

**直接调 Service 等于跳过了"参数绑定"这一层**，而且你在测试里会**"自觉"地把参数填对**。

更本质地说：

> **越权漏洞往往出在「层与层的接缝」上。**

**解法：必须走 MockMvc（或真实 HTTP），让参数真的从字符串被绑定成对象。**

**一句话**：**测"接口的安全性"，就要从接口的入口进 —— 自己构造 Service 入参，等于把攻击者最容易利用的那一层绕过去了。**

---

## 6.3 假绿：只断言"失败"，没断言"为什么失败"

**现象**

```java
assertThat(res.getInteger("code")).isEqualTo(0);   // ← 只断言"失败了"
```

测试是绿的，但它**证明不了任何事**。

**根因**

`submitOrder` 里的校验顺序是：**地址归属 → 购物车非空**。测试环境购物车是空的，所以：

- 地址归属校验**正常工作** → 报"用户地址为空"
- 地址归属校验**被删掉了** → 继续往下走 → 购物车是空的 → **同样返回 `code=0`**

**两种情况的断言结果完全一样，测试对 bug 无感。**

**解法：断言具体的失败原因**

```java
assertThat(res.getInteger("code")).isEqualTo(0);
assertThat(res.getString("msg")).isEqualTo(MessageConstant.ADDRESS_BOOK_IS_NULL);
```

用 `MessageConstant` 常量而不是字面量字符串，这样消息文案改了测试不会误报。

**注意"假绿"和"验证测试有没有牙齿"是两件事**：

- 断言太弱 → 假绿
- 要确认测试真的有牙齿 → **故意复现 bug，看测试会不会变红**

**具体做法**（本项目做过一次）：把关键那行代码注释掉，跑测试，确认**恰好对应的用例变红**，然后恢复。

```
复现 bug 后：
Tests run: 6, Failures: 3
  ✗ historyOrders_shouldOnlyReturnOwnOrders
  ✗ historyOrders_shouldNotFallBackToFullTable
  ✗ historyOrders_shouldIgnoreSpoofedUserId
```

**一句话**：**一个永远不会失败的测试等于没写。**

---

## 6.4 测试数据污染 → 用 `@Transactional` 自动回滚

**做法**

测试类/方法上加 `@Transactional`，Spring Test 会在每个测试方法结束后**自动回滚**。

于是你可以放心在测试里插"别人的订单""别人的地址"，**跑完库里一条都不剩**。

**验证过**：测试跑完后 `SELECT COUNT(*) FROM orders WHERE user_id IN (990001,990002)` = 0。

**⚠️ 失效的情况**

- 被测代码用 `REQUIRES_NEW` 开了新事务
- 被测代码 `try-catch` 吞掉异常后继续提交
- 用 `RANDOM_PORT` + 真实 HTTP（跨线程，事务不共享）

**另一个技巧**：测试用**很大的 id**（如 `990001` / `990002`）造数据，避开库里已有的真实数据，隔离性更好。本项目 `orders.user_id` 没有外键约束，所以不需要真的建用户行。

**一句话**：**测试的"数据隔离"和"身份隔离"都要设计** —— 前者用事务回滚，后者用专属的测试 id 段。

# 七、前端

## 7.1 路由守卫无限重定向 → 白屏

**现象**

登录后页面**完全空白**，控制台没有明显错误。

**根因**

引入 `role` 之前，登录页存进 localStorage 的是旧结构：

```json
{ "id": 1, "userName": "admin", "name": "管理员", "token": "..." }   ← 没有 role
```

而路由守卫有两条规则，在这条数据上**互相打架**：

```
规则①  没登录 → 跳 /login
规则②  已登录 → 不许待在 /login，送回自己的首页

旧数据同时触发：有 token（规则②认为"已登录"）
                但角色算不出首页（HOME_BY_ROLE[undefined] → undefined → || '/login'）

于是：/ → /login → /login → /login ...
vue-router 判定「导航守卫里无限重定向」，中止导航 → 整个页面白屏
```

**为什么重启服务、刷新都没用**：localStorage 是浏览器持久化的，跟服务重启无关。

**解法（两层）**

1. **根因**：`getLoginUser()` 校验结构，不只看 token

```java
if (!user || !user.token || !VALID_ROLES.includes(user.role)) {
    return null;      // 结构不合法（含旧版本遗留数据）→ 一律当未登录
}
```

2. **防复发**：抽出 `homeFor(user)`，建立不变量

> **`homeFor()` 返回 `/login`，当且仅当未登录**

守卫里也加显式保护：算出来是 `/login` 就**停下渲染登录页**，绝不 `next('/login')`。

**一句话**：**前端不能只看 token 判断"已登录"** —— 登录态是"token + 身份"两部分，**缺一半就是半登录状态，而半登录状态在带权限路由的应用里几乎必然产生死循环**。

## 7.2 Vite 监听锁住文件 → 写入报 `ReplaceFileW EIO (Win32 32)`

**现象**

用编辑器工具改 `src/` 下的文件，报：

```
ReplaceFileW EIO (Win32 32)
```

Win32 错误码 32 = `ERROR_SHARING_VIOLATION`（文件被占用）。

**根因**

Vite dev server 的文件监听（chokidar）**握着源文件的句柄**，而"原子替换式写入"需要 DELETE 权限，拿不到锁。

**解法（任选）**

- 停掉 dev server 再改（最干净）
- 用**普通写入**替代原子替换（普通写入只需要写权限，通常能和监听器共存）
- 有的编辑器和 Vite 能共存（取决于写入方式）

**一句话**：**"文件被占用"不一定是编辑器的问题，先看有没有 dev server / 监听进程开着。**

# 八、排查方法（元技能，比具体知识更值钱）

## 8.1 500 先看后端日志，别在代码里猜

**真实教训**：某次接口报 500，从 Java 代码看像是 `BeanUtils.copyProperties` 的问题（之前确实遇到过）。但**日志里是**：

```
java.sql.SQLIntegrityConstraintViolationException: Column 'delivery_status' cannot be null
```

**根因在 SQL 层，不在 Java 层。**

**教训**：我曾经"只验证了 Java 层就下结论"，结果判断错了方向。**真正该做的是分层验证** —— `copyProperties` 有没有崩是一层，SQL 能不能插进去是另一层。

**一句话**：**遇到 500 先读日志的最后一段堆栈，那才是最终答案。**

---

## 8.2 用探针程序验证语言/框架行为，别凭记忆

想确认 `BeanUtils.copyProperties` 在 `Integer → int` 且值为 null 时的行为，**不要猜**，写个独立小程序，用项目同样的依赖版本跑一遍：

```
java -cp "<spring-beans-5.3.22.jar>;<spring-core-5.3.22.jar>;<sky-pojo/target/classes>" Probe.java
```

几行代码，结论确定，还能看到确切的异常信息。

**一句话**：**对"框架的边界行为"（null 怎么处理、异常怎么包装），实测比记忆可靠。**

---

## 8.3 并发设计要用「真并发」验证

"两个并发请求"和"先后发两个请求"，测的**不是同一件事**。

- 顺序发 → 第二次会撞上"第一次已经清空的购物车" → **根本测不到抢占逻辑**
- 同时发 → 才能验证"只有一个赢"

**做法**：用 `HttpClient` 同时发出两个请求（`.PostAsync()` 两次再 `WaitAll`），而不是循环里调两次。

本项目用这个方式验证了"抢占式清空购物车"：**两个请求都返回 HTTP 200，但只有一个 `code=1`，数据库只多了一张订单。**

**⚠️ 顺带一个坑**：业务异常在本项目里返回的是 **HTTP 200 + `code=0`**，所以"两个请求都 200"不等于"都成功了"——**必须看响应体的 `code`，不能只看 HTTP 状态码**。

**一句话**：**验证并发，必须让两个请求真正同时在飞。**

---

## 8.4 用真实客户端验证推送

验证 WebSocket 推送，不要只看日志"我调用了 sendToAllClient"，而是**真的连一个客户端上去收消息**。

本项目验证结果：

```json
{"orderId":17,"type":1,"content":"订单号：202609212121051671"}
```

这一条同时证明了：**推送发出去了** + **内容是真实订单号而不是 null**。

**一句话**：**"我调用了"和"对方收到了正确的数据"是两件事。**

---

## 8.5 验证测试有效性（故意复现 bug）

见 6.3。**测试写完不算完，要证明它会失败。**

# 九、一句话总结（按重要性排序）

1. **越权漏洞不会报错** —— 它只是"数据范围不对"，手工测试永远发现不了，必须专门构造用例
2. **权限条件不能是可选的** —— 动态 SQL 表达业务筛选可以，表达权限约束是灾难
3. **能合并进数据库写操作的并发判断，就不要引入锁** —— CAS + 影响行数
4. **凡是参与金额计算的前端参数，要么后端重算，要么校验边界**
5. **"看起来能跑"和"逻辑正确"是两件事** —— 多个错误可能互相抵消，修一半反而引爆
6. **先看日志，再改代码** —— 判断错了层次，后面全白费
7. **一个永远不会失败的测试等于没写** —— 包括"断言太弱"造成的假绿
