> 上游依赖：统一登录（已上线）、C 端订单闭环（已完成）、管理端订单流转（已完成）。

> 生成时间：2026-09-26

## 2. ⚠️ 必须先解决的三个问题（第一个是阻塞项）

> **✅ 三个问题都已在 2026-10-04 解决**，结论全部落到代码里了：
> 2.1 拆出了 `rider.online` 列，派单筛选改成 `status = 1 AND online = 1`；
> 2.2 的落地方式与本节不同 —— `password` 没有进 `RiderDTO`，改由服务端固定成默认密码；
> 2.3 凌晨那个"派送中自动完成"任务已删除。
> 实施细节、与本节不一致的地方、验证证据见 **§12**。本节保留原文，作为当时的决策依据。

### 2.1 【阻塞】`rider.status` 一个字段背了两种互相冲突的含义

**证据**：同一个 `status` 字段被两处按完全不同的语义使用。

```java
// 用法一：登录时校验 —— 这是【账号启停】的语义
// LoginServiceImpl:80-84
// 状态校验（骑手 0=未上线不能用，用户/员工 0=禁用）
if (account.getStatus() == null || StatusConstant.DISABLE.equals(account.getStatus())) {
    throw new AccountLockedException(MessageConstant.ACCOUNT_LOCKED);   // "账号被锁定"
}

// 用法二：派单时筛选 —— 这是【在线/离线】的语义
// OrderServiceimplBusiness:211
List<Rider> riders = riderMapper.getStatus(RiderConstant.GO_ONLINE);   // 只挑"上线中"的
```

数据库列注释本身就是矛盾的：`'状态：1在线 0停用'` —— **一句话里说了两件事**。

**为什么这是阻塞项**：这期要做"骑手自己上线/下线"。只要一上线，下面这条就会**必现**（不是理论风险）：

> **骑手点一下"下线"，就再也登不进自己的账号了。**
> 因为下线把 `status` 改成 0 → 下次登录被 `LoginServiceImpl` 判定为"账号被锁定" → 而他改回来必须能登录。**骑手把自己锁在门外了，且无法自救。**

另外两个连带的坏处：

- **管理员停用**和**骑手离线**在库里长得一模一样，运营/客服无法区分，也没法分别统计
- 两种权力混在一个字段上：管理员和骑手**都能改同一个值**，谁后写谁生效

**产品建议：拆成两个字段，让两种权力各归其位**

| 字段 | 含义 | 谁能改 | 影响 |
|---|---|---|---|
| `status` | **账号状态**：1 启用 / 0 停用 | 只有管理员 | 登录时校验（保持现状） |
| `online` | **接单状态**：1 上线 / 0 离线 | 只有骑手本人 | 派单时筛选 |

配套改动：
- `rider` 表加一列 `online int NOT NULL DEFAULT 0`（默认离线 —— 新建的账号不该自动开始接单）
- `deliveryOrder` 的筛选条件由 `status = 1` 改成 `status = 1 AND online = 1`
- `rider.status` 的列注释改成只有"账号启停"一种含义
- 现有 4 条数据：`status=1` 的三位建议 `online=0`（要他们自己上线），`status=0` 那位保持

> 备选方案（不改表）：`status` 只表示账号启停，"在线"放 Redis（登录时写 key + TTL）。**不推荐** —— 多一个外部依赖，还要处理 key 过期和"骑手没主动下线但 key 过期了"的边界，比加一列复杂得多。

### 2.2 【小】`RiderDTO` 缺账号字段，建不出骑手

```java
public class RiderDTO {
    private Long id;
    private String name;
    private String phone;
    private Integer status;
    ...
}
```

`rider.username` 和 `rider.password` 都是 **NOT NULL**，但 DTO 里没有这两个字段 —— 所以"新增骑手"这个接口现在**传不了账号密码**。需要补 `username` / `password`（新增时必填；编辑时不接受传 `username`）。

### 2.3 【连带】凌晨的定时任务兜底，在有了真骑手之后是错的

`OrderTask.processDeliveryOrders` 每天凌晨 1 点，把"派送中"且下单超过 60 分钟的单**直接改成已完成**。

- 在**没有**骑手端的时候，这是个合理的兜底（不然单子永远卡在派送中）
- 有了骑手端之后，它会把**根本没送到的单标记成已完成** —— 用户投诉"我没收到但显示已完成"

**产品决定：本期把这个定时任务关掉。** 由骑手手动确认送达替代它。理由：一旦"送达"有了明确的操作人，就不该再有一个自动的假送达。

> 如果担心骑手忘记点送达，正确做法是"超时**告警**给人看"，而不是"自动置为已完成" —— 那属于下一期的运营需求。

## 5. 接口清单

约定：所有出参都是后端统一的 `Result{code,msg,data}`，`code=1` 成功；`code=0` + `msg` 是业务失败。下面只写 `data` 的结构。

### 5.1 管理端：骑手管理

#### R1 骑手分页查询

```
GET /admin/rider/page?page=1&pageSize=10&name=张
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `page` | ✅ | 页码，从 1 开始 |
| `pageSize` | ✅ | 每页条数，**上限 50**（超了报"页的记录量太大"，和 C 端一致） |
| `name` | ❌ | 按姓名模糊查 |

`data` = `PageResult`：`{ total, records: RiderVO[] }`

```json
{ "id": 1, "username": "13800000001", "name": "张三",
  "phone": "13800000001", "status": 1, "online": 1,
  "createTime": "2026-09-26 10:00:00" }
```

> ⚠️ **`RiderVO` 里绝不能有 `password`** —— 哪怕是 MD5。C 端 `/user/user/me` 当初就是靠 VO 白名单挡住 password 的，这里照做。

#### R2 新增骑手

```
POST /admin/rider
```
```json
{ "username": "13800000005", "password": "123456", "name": "李四", "phone": "13800000005" }
```

业务规则（**第 2 条是新增的硬规则，容易漏**）：

1. `username` 在 `rider` 表内唯一（库里有 `uk_rider_username`），重复 → "该账号已存在"
2. ⚠️ **`username` 还必须跨表唯一** —— 不能和 `employee`、`user` 表里的账号重名。
   因为统一登录是一条 `UNION ALL` 查三张表，**重名会导致命中 ≥2 行，登录直接被拒**（`ACCOUNT_CONFLICT`"该账号在多端重复，请联系管理员"）→ 等于建了一个谁都登不上去的账号。
   所以新增前必须查 `employee` + `rider` + `user` 三张表。
3. `password` 存 **MD5 十六进制**（和 `employee` 一致，`DigestUtils.md5DigestAsHex`）
4. 初始值：`status = 1 启用`、**`online = 0 离线`**（新建账号不该自动开始接单）
5. `phone` 必填，11 位

#### R3 编辑骑手

```
PUT /admin/rider
{ "id": 1, "name": "张三", "phone": "13800000009" }
```

- 只允许改 `name` / `phone`
- **不接受 `username`**（它是登录凭据，改了等于换人；真要改属于账号迁移，不做）
- **不接受 `password`**（改密码是另一个动作，本期不做 —— 需要就找管理员重置，走下一期）
- **不接受 `status` / `online`**：改状态走 R4，上下线只有骑手自己能操作

#### R4 启用 / 停用骑手账号

```
POST /admin/rider/status/0?id=5
```

| 参数 | 说明 |
|---|---|
| 路径 `status` | `1` 启用 / `0` 停用 |
| query `id` | 骑手 id |

业务规则：

1. **这是"账号级"操作，不是"上线/下线"**（见 §2.1）。停用后该骑手**立即无法登录**，已经登录的 token 在过期前仍然有效（JWT 无状态的已知特性，本期接受）
2. 停用**不改变** `online`
3. 停用时**不回收**他手上"派送中"的单 —— 本期不做（要做属于"骑手离职时的订单改派"，是独立需求）
4. 停用后 `deliveryOrder` 不会再挑到他（筛选条件含 `status = 1`）

#### R5 删除骑手 —— **本期不做，只做停用**

**产品决定：不提供删除接口。**

理由：骑手是历史订单的关联实体（`orders.rider_id`）。停用已经能达到"不再派单、不能登录"的全部目的，而物理删除只会留下悬空外键、并把"这人曾经送过哪些单"的关系切断。要真删，应该走"停用 + 数据归档"的流程，不是点一下就删。

### 5.2 骑手端：我的配送单

> 这 5 个接口的路径前缀 `/rider/**` 已经被拦截器强制要求 `RIDER` 角色，不需要额外配置。
>
> **实现位置**（R6–R8 和 R9–R10 分属两个 controller：一个管订单，一个管账号）：
> - R6 / R7 / R8 → `controller/rider/OrderController`，映射 `/rider/order`
> - R9 / R10 → `controller/rider/RiderController`，映射 `/rider`
>
> 各接口**实现后的最终契约**写在各小节末尾的「实施补充」里，差异汇总见 §12。
> 另外：本文件说到派单方法时用的是 `deliveryOrder`，代码里实际叫 `OrderServiceimplBusiness.orderSend`。

#### R6 我的配送单列表

```
GET /rider/order/list?page=1&pageSize=10&status=4
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `page` / `pageSize` | ✅ | 同上，`pageSize` 上限 50 |
| `status` | ❌ | 不传 = 全部指派给我的单；`4` 派送中；`5` 已完成 |

`data` = `PageResult`，`records` 是订单摘要：订单号、状态、下单时间、金额、**收货人 / 电话 / 地址**、菜品摘要。

> 🔒 **第一越权点。** 这个接口**不接受任何骑手 id 参数**。骑手身份只能来自 token（`BaseContext.getCurrentId()`），服务端**无条件用 token 里的 id 过滤**，并且要写成 SQL 的强制条件，不能是可选的 `<if>`。
> 这条和 C 端历史订单的 `userId` 是**完全相同**的要求 —— 漏了就是"骑手 A 看得到骑手 B 的单"。

**实施补充（2026-10-04，已验证）**

- **入参 DTO 是 `RiderOrderPageDTO`（`page` / `pageSize` / `status` 三个字段），刻意没有骑手 id**，所以 `?riderId=xxx` 在类型层面无处可绑 —— 这是第一道防线。
- **`rider_id` 的过滤写在 `OrderMapper.riderPageQuery` 的 SQL 里，不是可选 `<if>`**：`where rider_id = #{riderId}` 是骨架，`status` 才是可选筛选。参数名用 `@Param("riderId")` 显式绑定（不靠编译器的 `-parameters`）。
- **`status` 有白名单**，只放行 `不传 / 4 / 5 / 6`，其它值报「订单状态只能是派送中/已完成/已取消」。放行 `6` 是 §7 的要求（管理员取消派送中的单会留下 `status=6` 且 `rider_id` 有值）；`1/2/3` 结构上不可能属于骑手（派单是 `3 → 4` 一步绑定骑手），传了应当**报错**而不是静默返回空列表 —— 否则前端参数拼错时的表现是"这个骑手没单"，根本查不出来。
- **返回里只有 `orderDishes` 摘要字符串**（形如 `王老吉*1;`，**结尾带一个 `;`**，前端 `split(';')` 后过滤空串），**没有 `orderDetailList`** —— 那是 R7 的事。
- **一页固定两条 SQL**：先分页查订单，再按这一页的 id 批量查明细；**这一页为空时直接返回**，不去查明细（`in ()` 是 SQL 语法错误）。空数据返回 `total=0, records=[]`，**不是**报错。
- 明细是"按行循环查"而非批量（一页 10 单 = 11 条 SQL）。骑手手上单量小，本期接受。
- 排序 `order by order_time desc, id desc`（带 id 兜底：同一秒下的两单顺序才不会飘）。

#### R7 配送单详情

```
GET /rider/order/detail/{id}
```

`data` = 订单全字段 + `orderDetailList`，骑手关心的重点：收货人、电话、地址、备注。

> 🔒 **第二越权点。** 必须校验 `order.riderId == token 里的 id`。
> **校验失败时的错误信息要和"订单不存在"完全一致**，不要提示"这不是你的单" —— 否则等于告诉对方"这个订单确实存在"，属于信息泄露。C 端订单详情就是这么做的，照抄。

**实施补充（2026-10-04，已验证）**

- 实现走的是"先 `getById` 再在 Java 里比归属"，**没有**按 §6.1 的表格把归属塞进 WHERE。两条分支（查不到 / 不是你的单）抛的是同一句 `ORDER_NOT_FOUND`，所以"错误信息完全一致"这条要求是满足的。
  代价：那两句话是**两处独立的字面量**，将来只改一处就会泄露存在性。想更稳可以换成 `where id = #{id} and rider_id = #{riderId}`，让"查不到"成为唯一的失败原因。
- **归属判断用的是 `orders.getRiderId()`，不是 `getUserId()`。** 后者是"下单用户"的 id，和骑手 id 是两张表两个体系 —— 比错了会既打不开自己的单，又在两个 id 数字撞上时放行别人的单。
- **这里没有 `status` 条件**：已取消(6)、已完成(5) 的单详情都要能正常打开（§7 的要求）。加了 `and status = 4` 的话，历史 tab 里点进去会说"订单不存在"。
- 返回 `OrderVO` + `orderDetailList`；**不填 `orderDishes`**（详情页渲染的是逐项明细，摘要字符串是列表页用的）。

#### R8 确认送达

```
PUT /rider/order/complete/{id}
```

业务规则：

1. 只允许 **4 派送中 → 5 已完成**，同时写 `delivery_time`
2. ⚠️ **归属校验和并发校验要合成一条 SQL**，不要写成"先查再改"：

```sql
update orders
set status = 5, delivery_time = now()
where id = ? and status = 4 and rider_id = ?      -- ← rider_id 就是归属校验
```

   - 影响行数 = 1 → 成功
   - 影响行数 = 0 → 三种可能：**不是你的单** / 状态已变 / 订单不存在。再查一次决定报哪个错（照抄 C 端 `OrderSupport.throwCasFailure` 的思路）
3. **为什么必须是一条 SQL**：先 `select` 判断归属、再 `update`，中间有窗口 —— 而这期是"送达"，写错就是**把别人的单标记成已送达**。归属条件和状态条件是同一件事的两面，放同一条 SQL 里就没有窗口了
4. 幂等性：重复点送达 → 第二次影响行数为 0 → 报"订单状态错误"，不会写第二次 `delivery_time` ✓

**实施补充（2026-10-04，已验证）**

- SQL 是 `OrderMapper.updateCompleteByRider`：`where id = #{id} and status = 4 and rider_id = #{riderId}`，和本节一致。
- **影响行数为 0 时的处理偏离了本节的"照抄 throwCasFailure"**：那个方法回查用的是**不带归属条件**的 `getById`，结果"别人的单（存在）"会得到「订单状态错误」、「不存在的 id」得到「订单不存在」—— 两句话不一样就泄露了订单是否存在。
  改成了 `OrderSupport.throwRiderCasFailure(id, riderId)`：回查走带 `rider_id` 的查询，两种情况都得到 null、都是「订单不存在」，和 R7 的口径一致。
- 单已被取消时报「订单已取消」，而不是笼统的状态错误（`throwCasFailure` 原本就有这个区分）。
- 入参只有路径里的订单 id，不需要订单号/金额之类的东西。
- 失败时**不会**改动订单的任何字段 —— 有测试专门断言"别人的单状态和 `delivery_time` 都没变"。

#### R9 上线 / 下线

```
PUT /rider/status/1
```

| 参数 | 说明 |
|---|---|
| 路径 `status` | `1` 上线 / `0` 离线 |

业务规则：

1. 只改 `online` 字段，**绝不碰 `status`**（§2.1）
2. 骑手只能改**自己**的（id 从 token 取）
3. 影响：`deliveryOrder` 只会挑 `status = 1 AND online = 1` 的骑手
4. 下线**不影响**手上已经派给他的单 —— 他仍然要送完（否则单会卡住）。本期不做"下线时把手上的单退回"

**实施补充（2026-10-04，已验证）**

- 路径 `status` 只放行 `1 / 0`，否则报「接单状态只能是 1（上线）或 0（离线）」（常量 `RIDER_ONLINE_STATUS_INVALID`，和账号启停那句 `RIDER_STATUS_INVALID` 分开写）。
- 用的是 `RiderMapper.updateOnline`（`update rider set online = ?, update_time = now() where id = ?`），**只改 online 一列**。
- **刻意没用 CAS**：上下线是"把值设成某个数"，不是状态流转，连点两次都应该成功；加 `online <> ?` 这样的条件反而会让第二次点击报错。需要 CAS 的是 R8 那种"必须从 4 变成 5"的流转。
- **账号被停用的骑手也能上线，而且无害**：停用只拦登录、不作废已签发的 token（§7 已接受），但派单筛的是 `status = 1 AND online = 1`，所以他上线了也接不到单。刻意不加这个判断，免得骑手收到一个自己看不懂的报错。
- 派单筛选改成了 `RiderMapper.listAvailable()`：SQL 写死 `status = 1 and online = 1`、**不留参数**，原先那个只有一个调用方的 `getStatus(int)` 已删除。
- **下线之后仍然能正常登录** —— 这是 §2.1 那个拆分做对了的直接证据，真机验证过。

#### R10 当前骑手信息

```
GET /rider/me
```

`data` = `{ id, username, name, phone, status, online }`

用途：骑手端顶栏显示"张三 · 上线中"，并据此渲染上线/下线开关的初始状态。

> 同样**不返回 `password`**。

**实施补充（2026-10-04，已验证）**

- 复用了 `RiderVO`（没有为 R10 新建专用 VO），所以响应里**多一个 `createTime`**；`password` 依然没有，有测试从响应原文里查过一遍。
- **人不存在时（token 有效但库里没这个骑手）抛 `UserNotLoginException` → HTTP 401**，和 C 端 `/user/user/me` 的处理一致。理由：这种情况 token 本身是有效的，只是它指向的人没了；回 200+code=0 的话前端只弹 toast、不清 token，死 token 会一直躺在 localStorage 里，每个请求重复弹同一句话 —— 状态不会自愈。
- **骑手端首屏依赖它**：顶栏的"张三 · 上线中"和上线开关的初值都取这个接口，所以它是骑手端登录后的第一个请求。

## 6. 三个贯穿全期的硬规则

这几条不是建议，是"上线前必须满足"的条件。

### 6.1 订单相关的写操作，归属校验一律进 SQL 的 WHERE

| 接口 | WHERE 必须包含 |
|---|---|
| R7 详情 | `rider_id = 当前骑手` |
| R8 送达 | `rider_id = 当前骑手 AND status = 4` |
| R6 列表 | `rider_id = 当前骑手`（强制条件，不是可选 `<if>`） |

**为什么**：C 端刚踩完这个坑 —— 8 个按 id 操作订单的接口里，凡是漏了归属校验的都能被换 id 越权。骑手端更危险：**"骑手看自己的单"看起来天然就是过滤过的**，很容易在列表里老老实实过滤了，却在 `detail/{id}`、`complete/{id}` 这种"按 id 操作"的地方忘掉。

### 6.2 状态变更一律用 CAS，不用"先查再改"

R8 送达、R4 启停都是状态变更，判断"能不能改"和"动手改"必须在同一条 SQL 里。项目里已有 6 个 CAS 方法（5 个管理端订单流转 + `updateStatus` 支付），照这个套路写。

### 6.3 对外返回用 VO，不返回实体

`RiderVO` 不含 `password`。理由同 C 端 `/user/user/me`：**在类型层面**排除敏感字段，比"记得在某个地方 setNull"可靠。

## 7. 边界与异常

| 场景 | 期望行为 |
|---|---|
| 派单时一个上线的骑手都没有 | 已有的 `RIDER_NOT_FOUND`"暂无可用骑手，请稍后再试"，**本期不改** |
| 骑手停用后、token 还没过期就访问 `/rider/**` | 拦截器只看 token 签名和角色，**不会**查库 → 仍能访问。本期接受（JWT 无状态的固有特性）。真要立刻失效需要引入黑名单，属于下一期 |
| 骑手看一张"已取消"的单 | 正常返回（如果这张单曾指派给他）。状态以订单为准 |
| 骑手送达时订单已被管理员取消 | CAS 影响行数 0 → 报"订单状态错误" |
| 两个骑手同时点同一张单的送达 | 不可能 —— 一张单只绑定一个骑手。但**重复点**会出现，由 CAS 兜住 |
| 管理员停用了一个正在送单的骑手 | 单子不受影响，他仍能送完（本期不做改派） |
| 新增骑手时账号和员工重名 | 必须拒绝，提示"该账号已存在"（见 R2 规则 2） |

### 12.2 与设计不一致的地方（都是有意的）

1. **§2.2 的 `password` 没有进 `RiderDTO`。** 设计写的是"新增时管理员填账号密码"，实现改成**服务端固定成默认密码 `123456`**（`PasswordConstant.DEFAULT_PASSWORD` 的 MD5）；新增表单只有姓名 / 账号 / 手机号，弹窗里提示初始密码。改密码本期不做（员工侧也没有）。
2. **R6 用了新的 `RiderOrderPageDTO`**，没有复用 `OrdersPageQueryDTO` —— 后者带着 `number / phone / beginTime / endTime / userId`，其中大部分是 R6 不该接受的入参。
3. **R6 的查询是新写的 `OrderMapper.riderPageQuery`**，没有往共用的 `pageQuery` 上加可选的 `riderId`。那条 SQL 正被 C 端历史订单和管理端条件查询同时用着；加可选条件等于把骑手的隔离寄托在"Service 记得 set"上，而且会顺带扩大那两个接口的入参面。
4. **R8 失败时用 `throwRiderCasFailure` 而不是 `throwCasFailure`** —— 理由见 R8 的实施补充（避免泄露订单是否存在）。
5. **R9 不用 CAS**；**R10 复用 `RiderVO`**（因此多返回一个 `createTime`）。
6. **控制器拆成了两个**：`OrderController`（`/rider/order`，R6–R8）和 `RiderController`（`/rider`，R9–R10）。设计里没写这个拆分，但 R9/R10 是账号接口，挂到 `/rider/order` 下面语义不对。原来的 `controller/rider/RiderController`（映射 `/rider/order`）已改名为 `OrderController`。
7. **`orderSend` 的选人条件**从"只按 `status`"改成 `RiderMapper.listAvailable()`（`status = 1 AND online = 1`），并删掉了只剩一个调用方的 `getStatus(int)`。

### 12.3 §2.3 的补充决定：管理端的"完成"按钮保留，但改定位

§2.3 只决定了关掉凌晨的自动完成任务。实施时还要回答"管理端的 `PUT /admin/order/complete/{id}` 撤不撤"，结论是：

**保留，定位从"正常完成路径"改成"人工兜底"。** 因为如果两个都撤掉，一单进了"派送中"之后就只剩骑手本人能推动它 —— 骑手忘了点、手机没电、账号被停用，这单就永远卡住，用户那边一直显示派送中，而全系统没有任何界面能救它。

- 自动完成的问题不是"有人兜底"，而是"**没有**人做决定"：凌晨静默改状态、无人知晓，用户投诉"我没收到但显示已完成"时，系统里查不出这单是谁改的。管理端是有人按、有 CAS 限制（`where status = 4`）、日志里看得见。
- 前端在那个按钮上把二次确认的文案改成说清后果：「正常路径由骑手在骑手端确认送达，管理员代确认属于异常兜底；订单将标记为已完成，且不可撤销」。
- **已知不足：没有操作留痕。** 谁在什么时候代确认的，库里没记（`orders` 没有对应字段）。要做到可审计需要加列，建议和"骑手离职时的订单改派"一起排期。

顺带一个发现：**被删掉的那个任务本身还带着一个 bug** —— 它用的是非 CAS 的 `orderMapper.update(orders)`（拿着 `select` 出来的整行快照写回所有非 null 字段），和 `processTimeoutOrders` 修掉的那个属于同一类：骑手正好在这个窗口里确认送达，`delivery_time` 会被快照里的 null 覆盖掉。所以**不要照原样复活它**，理由写在 `OrderTask` 的类注释里。

### 12.4 一条钉住产品决定的测试

`OrderTaskTest.onlyTimeoutTaskShouldBeScheduled` 用反射列出 `OrderTask` 里所有带 `@Scheduled` 的方法，断言**只有 `processTimeoutOrders`**。

理由是那个被删的任务每天凌晨 1 点才触发，测试里根本调不到它；而它一旦被加回来，后果是"没送到的单被标成已完成"。这种事不能靠"记得别加"，得让加的人先红一次，然后去读类注释里的三条理由。

### 12.6 §11 开放问题的结论

1. **`online` 的历史数据**：现有 4 个骑手全部 `online = 0`（等骑手自己上线）。代价是演示时要先点一次"上线"才会被派单 —— 但这正好让 §8.3 的全链路演示更完整。
